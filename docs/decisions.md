# 설계 결정 기록

각 결정의 배경과 근거를 남긴다. 나중에 "왜 이렇게 했지?"를 되짚기 위한 문서다.

---

## ADR-001. Transit형 KMS로 간다

**상태**: 확정

**배경**
KMS를 두 가지 형태로 만들 수 있다.
- kv형: 값을 받아 암호화해 저장하고, 나중에 복호화해 돌려준다
- transit형: 저장하지 않고 암복호화 연산만 제공한다

**결정**
Transit형.

**근거**
- AWS KMS, GCP Cloud KMS가 transit형이다. "실제 클라우드 KMS 재현"이라는 목표에 부합한다
- 쿠버네티스 KMS Provider 규격 자체가 `Encrypt`/`Decrypt`만 요구하고 저장을 요구하지 않는다.
  저장 기능을 만들어도 쿠버네티스는 쓰지 않는다
- 저장 부담(영속성, 백업, 용량)이 작아 졸업 프로젝트 규모에 현실적이다

**대가**
데모 임팩트가 약하다 — "문자열 넣으면 암호문 나온다"가 전부로 보일 수 있다.
이를 쓰는 얇은 데모 앱을 부록으로 둬서 보완한다.

## ADR-002. API를 Transit/Admin 두 평면으로 분리한다

**상태**: 확정

**배경**
단일 HTTP 서버(`:8200`)에 암복호화와 키 관리, init/unseal이 모두 섞여 있었다.
클러스터 안의 어떤 파드든 8200에 접속하면 키를 만들고 지울 수 있었다.

**결정**
- Transit 평면: TCP `:8200` — 암복호화, rewrap
- Admin 평면: 유닉스 도메인 소켓 — 키 관리, init/unseal

**근거**
"키를 사용하는 권한"과 "키를 관리하는 권한"은 다르다
(AWS KMS의 키 관리자/키 사용자 분리, Azure의 Crypto Officer/Crypto User와 동일한 원칙).
관리 기능을 네트워크에서 아예 제거하면, 권한 체계를 만들기 전에도 구조적으로 보호된다.

**대가**
브라우저는 유닉스 소켓에 접속할 수 없다. 웹 UI가 동작하지 않게 되어,
별도 프로세스인 관리 API가 필요해졌다(ADR-005).

## ADR-003. 인증은 apiserver TokenReview가 아닌 로컬 JWT 서명 검증

**상태**: 확정

**배경**
Transit API 요청자를 식별해야 한다. ServiceAccount 토큰 검증 방법은 두 가지다.
- kube-apiserver의 TokenReview API 호출
- 서명 공개키로 로컬에서 JWT 검증

**실험**
kind 클러스터에서 static pod를 띄워 확인했다.

```bash
# /etc/kubernetes/manifests/ 에 매니페스트 배치 (serviceAccountName: default 명시)
crictl exec <container> ls /var/run/secrets/kubernetes.io/serviceaccount/
→ No such file or directory
```

**static pod에는 ServiceAccount 토큰이 자동 마운트되지 않는다.**
토큰 주입은 kube-apiserver의 admission controller가 수행하는데,
static pod는 kubelet이 매니페스트를 직접 읽어 생성하므로 이 과정을 건너뛴다.
`kubectl get pods`에 보이는 것은 사후 등록되는 mirror pod일 뿐이다.

**결정**
로컬 JWT 서명 검증. `/etc/kubernetes/pki/sa.pub`를 읽어 서명을 확인한다.

**근거**
- TokenReview를 쓰려면 KMS가 apiserver 접근 자격을 따로 마련해야 한다
- 암복호화는 요청마다 일어나는 핫패스다. 매 요청 apiserver 왕복은 지연이 크다
- KMS가 컨트롤 플레인 노드의 static pod라는 점을 활용할 수 있다
- apiserver가 죽어도 암복호화가 계속 동작한다

**한계**
토큰 폐기(revocation) 여부를 확인할 수 없다.
쿠버네티스의 projected token은 주기적으로 갱신되므로 실질적 노출 창은 제한적이지만,
명시적 한계로 문서화한다.

## ADR-004. 인가는 자체 정책이 아닌 SubjectAccessReview

**상태**: 확정

**배경**
"이 요청자가 이 키에 이 동작을 해도 되는가"를 판단해야 한다.
- 자체 정책 저장소를 두고 KMS가 직접 판단 (HashiCorp Vault 방식)
- kube-apiserver의 SAR에 위임 (쿠버네티스 RBAC 활용)

**결정**
SubjectAccessReview.

RBAC 어휘 매핑:
```yaml
apiGroups: ["kms.local"]
resources: ["keys"]
resourceNames: ["demo"]
verbs: ["encrypt", "decrypt", "rewrap"]
```

**근거**
- 정책 저장소, 편집 API, 관리 UI, 백업을 따로 만들지 않아도 된다
- 관리자가 `kubectl`로 Role/RoleBinding을 다루면 된다. 권한 관리가 표준 도구로 통일된다
- 검증된 시스템에 위임하는 것이 자체 구현보다 안전하다

**검증**
kind 클러스터에서 실제 apiserver를 상대로 확인했다.
team-a의 ServiceAccount에 `demo` 키 `encrypt`만 허용한 뒤:
- encrypt → 200
- decrypt → 403 (같은 토큰·같은 키인데 동작에 따라 갈림)
- team-b 토큰으로 encrypt → 403 (네임스페이스 격리)

가상 리소스와 커스텀 verb로 SAR이 성립함을 실증했다.

**대가**
ADR-003에서 피하려던 apiserver 자격 증명 문제가 돌아온다.
kubeconfig 또는 전용 SA 토큰을 hostPath로 제공해야 한다.
요청마다 apiserver를 부르는 지연은 짧은 TTL 캐싱으로 완화한다.

**부수 결정**
- 캐시 TTL 기본 10초. 허용·거부 모두 캐싱
- apiserver 장애 시 fail-closed(거부)가 기본. 보안 도구이므로 판단 불가 시 거부가 안전하다
- 장애 시 내린 폴백 판단은 캐싱하지 않는다 — TTL 동안 굳어지면 곤란하다

## ADR-005. 관리 API는 별도 프로세스

**상태**: 확정

**배경**
ADR-002로 관리 기능이 유닉스 소켓으로 이동해 웹 UI가 동작하지 않게 되었다.
브라우저가 소켓에 접속할 방법이 없다.

**결정**
HTTP를 받아 admin.sock으로 투명 중계하는 별도 프로세스(`cmd/admin-api`)를 만든다.
웹 UI도 이 프로세스가 서빙한다.

**근거**
- KMS 서버는 static pod로 배포되어 제약이 많다(ConfigMap 불가, SA 토큰 없음).
  관리 API는 일반 파드로 자유롭게 배포할 수 있다
- 웹 UI와 TLS 종단 같은 부가 기능을 KMS 본체에 섞지 않아 공격 표면을 줄인다

**중계 방식**
투명 프록시를 택했다. 요청을 해석하지 않고 경로/메서드/헤더/바디를 그대로 넘긴다.
구현이 짧고 KMS API가 바뀌어도 관리 API를 고치지 않아도 된다.

감사 로그나 관리자 인증을 넣으려면 명시적 라우팅으로 전환해야 한다. 추후 과제.

**미해결**
관리 API는 기동 시 admin.sock 존재를 확인하고 없으면 종료한다.
쿠버네티스에서 KMS보다 먼저 뜨면 CrashLoopBackOff가 된다.
재시작 정책으로 넘길지, initContainer로 대기시킬지 매니페스트 작업 시 결정한다.

## ADR-006. 배포 seal은 shamir

**상태**: 잠정 확정 (TPM 확보 시 재검토) — TPM 모드 추가는 [ADR-010](#adr-010-봉인-방식-이전과-tpm-자동-해제)

**배경**
서버 부팅 시 루트 키를 메모리에 올려야 KMS를 쓸 수 있다. 누가 풀어줄 것인가.

구현된 seal 4종의 적합성:

| seal | 가능 여부 | 사유 |
|---|---|---|
| k8s | ❌ | 루트 키를 K8s Secret에 두는데, 그 Secret을 암호화하는 것이 이 KMS. 순환 |
| dev | ❌ | 패스프레이즈가 매니페스트에 평문. 키 저장소와 같은 디스크에 있게 되어 디스크 탈취 시 무방비 |
| tpm | ❌ (현재) | 인스턴스에 `/dev/tpm*` 없음. OCI Shielded Instance로 재생성하면 가능할 수 있으나 A1 셰이프 지원 여부 미확인 |
| shamir | ✅ | 사용 가능 |

**결정**
shamir. 기본 5조각, threshold 3.

**대가 — 부팅 공백**
노드 재부팅 시 KMS가 sealed 상태로 뜬다.
관리자가 조각을 입력할 때까지 apiserver는 암호화된 Secret을 읽을 수 없다.

이를 약점이 아니라 설계 선택으로 다룬다:
"자동 복구보다 정족수 기반 통제를 우선했다.
재부팅 시 관리자 개입이 필요한 대신, 단일 관리자나 디스크 탈취로는 루트 키를 얻을 수 없다."

**TPM에 대한 입장**
구현과 기능 검증은 완료했으나, 실험 환경에 하드웨어 TPM이 없어 시뮬레이터로만 검증했다.
실제 보안 보장은 하드웨어 TPM이 있는 환경에서 성립한다. 이 제약을 명시한다.

## ADR-007. 메트릭은 별도 포트

**상태**: 확정

**배경**
Prometheus가 `/metrics`를 수집해야 한다. 어느 평면에 둘 것인가.

**결정**
전용 포트 `:9100`. 인증을 붙이지 않는다.

**근거**
- Transit에 두면 인증이 켜진 상태에서 Prometheus도 토큰이 필요해진다
- 메트릭이 애플리케이션 트래픽과 같은 경로로 노출되지 않게 분리한다
- 네트워크 정책으로 Prometheus만 접근하도록 제한하기 쉽다

**제약**
민감 정보를 메트릭에 포함하지 않는다.
키 이름을 라벨로 쓰지 않는다 — cardinality 폭발과 정보 노출 양쪽 문제다.
주체·네임스페이스도 같은 이유로 라벨에서 제외한다.

## ADR-008. 인가 클라이언트에 명시적 QPS/Burst를 설정한다

**상태**: 확정

**배경 — 실측으로 발견한 버그**
인가 캐시 비활성화(`KMS_AUTHZ_CACHE_TTL=-1`, ADR 아님 — 별도 수정 사항)
상태에서 `cmd/bench`로 성능을 측정하자 처리량이 정확히 **5 ops/sec**로
고정되고, 지연이 **199.9~201.4ms** 범위에 몰렸다. `kms_authz_sar_duration_
seconds` 히스토그램을 보면 패턴이 뚜렷했다:

- 처음 10건: 5ms 이내
- 그 뒤 62건: 100~250ms (평균 약 200ms)

처음 10건이 빠르고 그 뒤로 정확히 "초당 5개"로 멈춘다는 패턴은 토큰
버킷 속도 제한의 전형적인 서명이다. `grep -rn "QPS|Burst|RateLimiter"
internal/authz/ cmd/server/`가 아무것도 찾지 못해 확인했다: `internal/
authz`가 만드는 `*rest.Config`에 QPS/Burst를 설정하지 않아 client-go
기본값(QPS 5, Burst 10)이 그대로 적용되고 있었다. 처음 10건은 버스트
용량으로 즉시 통과하고, 그 이후로는 토큰이 초당 5개만 채워져 매 요청이
토큰 하나를 기다리느라 평균 200ms(1/5초)씩 대기한 것이다.

**영향 — 성능 문제가 아니라 가용성 버그**
캐시가 적중하는 동안은 SAR 호출 자체가 일어나지 않아 드러나지 않는다.
하지만 캐시 미스가 동시에 몰리면(예: 다수의 워크로드가 동시에 처음
호출하거나, RoleBinding 변경으로 캐시가 한꺼번에 무효화된 뒤):

1. 동시 요청 N개가 초당 5개 토큰을 나눠 쓴다 → 대기 시간이 최대 N/5초까지
   늘어난다.
2. `KMS_AUTHZ_TIMEOUT`(기본 3초)을 넘기면 SAR 호출 자체가 타임아웃으로
   실패한다.
3. `KMS_AUTHZ_FAIL_OPEN`이 기본값(`false`, fail-closed)이면 그 요청은
   거부된다 — **정상적인 권한을 가진 요청이 403을 받는다.**

즉 "느리다"가 아니라 "허가된 호출자가 임의로 차단당할 수 있다"는
가용성 문제다. 동시 요청이 15개만 몰려도(N/5=3초) 이미 타임아웃
경계에 걸린다.

**결정**
`internal/authz.NewClientFromEnv`가 만드는 `*rest.Config`에 QPS/Burst를
명시적으로 설정한다. `KMS_AUTHZ_QPS`/`KMS_AUTHZ_BURST` 환경변수로
노출하며, 해석 규칙은 `KMS_AUTHZ_CACHE_TTL`과 동일하게 맞춘다: `0`은
기본값, 양수는 그 값, 음수(둘 중 하나라도)는 클라이언트 측 속도 제한
자체를 비활성화(`flowcontrol.NewFakeAlwaysRateLimiter()`)한다.

**기본값: QPS=50, Burst=100**

- client-go 기본값(5/10)은 가끔 list/watch하고 드물게 patch하는
  컨트롤러용 값이다. 이 클라이언트는 캐시 미스마다 매번 호출하는
  핫패스라 성격이 다르다 — 이번 버그가 그 증거다.
- `Burst = 2×QPS`는 짧은 스파이크를 흡수하는 통상적인 비율이다.
- `SubjectAccessReview` Create는 etcd를 쓰지 않는 가벼운 승인 심사
  호출이다. 단일 KMS 인스턴스가 거는 50 QPS는 apiserver 전체 처리
  예산에서 무시할 수준이고, 웬만한 API Priority and Fairness(APF)
  우선순위 레벨의 동시성 셰어 안에도 넉넉히 들어간다. 다만 정확한
  셰어는 클러스터 구성(APF 설정)에 따라 다르므로, 매우 작은 클러스터라면
  운영자가 환경변수로 낮춰야 할 수 있다 — 그래서 하드코딩하지 않고
  노출한다.
- Burst=100이면 캐시가 한꺼번에 비워지는 상황에서 최대 100개까지
  즉시 통과하고 나머지는 초당 50개로 유입 제한된다. 동시 요청이
  대략 150개 이하인 흔한 스파이크는 `KMS_AUTHZ_TIMEOUT` 기본값(3초)
  안에 큐가 풀려 이번에 발견한 가용성 버그가 재발하지 않는다. 그보다
  큰 스파이크가 예상되면 이 값을 올리거나, 캐시 TTL을 늘려 미스 자체를
  줄이는 쪽을 먼저 검토해야 한다.

**측정 가시성**
`kms_authz_sar_duration_seconds`는 rate limiter 대기와 apiserver
왕복을 합쳐서 측정해, 이번 문제를 메트릭만 보고는 바로 구분하기
어려웠다(히스토그램 버킷 분포를 직접 들여다봐야 했다). 그래서
`kms_authz_apiserver_roundtrip_seconds`를 추가했다 — `rest.Config.
WrapTransport`(client-go가 공식적으로 지원하는 확장점, client-go 자신의
메트릭 계측도 같은 방식을 쓴다)로 순수 HTTP 왕복 시간만 따로 기록한다.
두 히스토그램의 `_sum`을 비교하면 rate limiter 대기 시간만 분리해서
볼 수 있다 — 이번 버그를 메트릭만으로 즉시 알아챌 수 있게 하는 것이
목적이다. 요청 하나당 "대기만"을 정확히 떼어내는 더 정밀한 방법(컨텍스트
누적 변수 등)도 가능하지만, 구현 복잡도 대비 얻는 정밀도가 크지 않아
이번 범위에서는 두 히스토그램의 차이로 보는 선에서 멈췄다.

**제약**
- QPS/Burst는 하나의 rate limiter를 함께 구성하는 값이라, 둘 중
  하나만 "비활성화"할 수는 없다 — 어느 한쪽이라도 음수면 전체를 끈다.
- 속도 제한을 비활성화하면 이 클라이언트에 대한 보호는 apiserver 쪽
  API Priority and Fairness만 남는다. 기동 로그에 경고를 남긴다.

## ADR-009. 키 소유 모델은 C+B (이름의 네임스페이스가 판단 네임스페이스)

**상태**: 구현 완료, 서버 적용 전 (이전: `scripts/migrate-rbac-cb.py`, 절차: [docs/release/kms-core-apply.md](release/kms-core-apply.md))

**배경**
ADR-004의 SAR은 처음에 "요청한 ServiceAccount의 네임스페이스"를 namespace로 보냈다(모델 A). 키 저장소에는 네임스페이스
개념이 없으니 키는 전역 목록 하나이고, 어느 팀이든 자기 네임스페이스에 Role만 만들면 *아무 키*에 권한을 줄 수 있었다.
즉 **키의 주인이 아닌 팀이 그 키의 권한을 스스로 발급**할 수 있다 — 키 이름을 알기만 하면 된다.

**결정 — 모델 C+B**
- 이름에 점이 하나 있는 키 `<ns>.<name>`은 `<ns>` **소유**. SAR의 namespace는 `<ns>`, resourceName은 키 전체 이름.
  그 네임스페이스의 Role/RoleBinding만 효력이 있다. 다른 네임스페이스의 SA도 소유 팀이 RoleBinding subjects에
  넣어 주면 쓸 수 있다(소유 팀이 허용 범위를 통제한다).
- 점 없는 키는 **클러스터 전역 키**. SAR을 namespace 없이(클러스터 범위) 보내므로 ClusterRole/ClusterRoleBinding으로만
  허용된다. 클러스터 관리자만 전역 키 권한을 줄 수 있다.
- 이름 규칙: `<ns>`는 DNS-1123 label, 점은 최대 1개. 기존 키(점 없음)는 그대로 유효하고 저장 형식 변경은 없다.
- SAR 캐시 키는 (주체, 판단 네임스페이스, 키, 동작).

**A와 비교**
| | A (요청자 ns) | C+B (키 이름의 ns) |
|---|---|---|
| 권한을 주는 주체 | 요청자 네임스페이스의 Role 작성자 | 키 소유 네임스페이스의 Role 작성자 / 전역 키는 클러스터 관리자 |
| 남의 키 접근 | 이름만 알면 자기 ns에 Role을 만들어 가능 | 소유 팀의 RoleBinding 없이는 불가 |
| 여러 ns가 한 키 공유 | ns마다 Role | 소유 ns의 RoleBinding 하나에 subjects 추가 |
| 키 저장소 | 변경 없음 | 변경 없음 (이름 규칙만 확장) |

"왜 B만(소유 ns 하나)이 아니라 C+B인가": 데모 키(`demo`)나 플랫폼 공용 키처럼 *특정 팀 소유가 아닌* 키가 필요하다. 그것을
ClusterRole로만 허용되는 전역 키로 분리해, 소유자가 없는 키의 권한 발급을 클러스터 관리자에게 모은다.

**기존 키 이전**: 기존 키는 모두 점이 없으므로 전역 키가 된다. 따라서 *점 없는 키에 대한 네임스페이스 Role/RoleBinding*은 새
서버에서 효력을 잃는다. `scripts/migrate-rbac-cb.py check`가 그런 권한을 표로 찾고(resourceNames 없는 Role은 경고),
`generate`가 같은 키·verb·주체의 ClusterRole+ClusterRoleBinding(이름 `kms-cb-<키>-<verbs>`)을 파일로 만든다.
**서버 재시작 전에 ClusterRole을 먼저 적용**하면 권한 공백이 없다(새 ClusterRole은 옛 서버에서도 무해). 기존 Role은 지우지 않는다(되돌리기).
KMS v2 경로(apiserver → 유닉스 소켓 → `k8s-secrets`)는 SAR을 거치지 않으므로 영향이 없다.

**대가**: 전역 키의 권한 발급이 클러스터 관리자에게 집중된다(의도). 이전 중 놓친 권한은 403으로 드러난다(fail-closed).

## ADR-010. 봉인 방식 이전과 TPM 자동 해제

**상태**: 구현·시뮬레이터 검증 완료, **배포 보류** (재개 절차: [docs/release/tpm-seal.md](release/tpm-seal.md))

**배경**
ADR-006의 대가는 "부팅 공백"이다 — 재부팅할 때마다 사람이 Shamir 조각 3개를 넣어야 클러스터가 Secret을 읽는다.
TPM 봉인은 이 공백을 없앤다. 그런데 운영 클러스터의 Secret은 *현재 루트 키로만* 읽힌다.
봉인 방식을 바꾸는 기능이 루트 키를 새로 만들면 모든 Secret이 영구히 읽히지 않는다.

**결정**

1. **루트 키 불변.** 어떤 경로에서도 기존 저장소의 루트 키를 새로 만들거나 덮어쓰지 않는다. 이전(`POST /v1/sys/seal-migrate`)은
   봉인 해제 상태의 *메모리에 있는 같은 루트 키*를 다시 봉인(TPM) 하거나 다시 나눌(Shamir) 뿐이다. 그래서 봉인 상태에서는 이전할 수 없다(409).
   `InitTPM`(새 키 생성)은 이전에 쓰지 않고, 기존 키를 받는 `SealExisting`을 따로 두었다.
2. **init 기록이 진실의 원천.** 어떤 방식으로 해제할지는 환경변수가 아니라 저장소의 `initialization.json`의 `seal` 값이 정한다.
   `KMS_SEAL_ALLOWED`(기본 `shamir,tpm`)는 허용 목록일 뿐이며, 기록이 목록 밖이면 기동을 거부한다. dev·k8s는 계속 거부한다.
   기록은 `format_version` 2로 올리되 v1(필드 없음 = shamir)을 계속 읽는다. aad가 버전·seal을 포함해 디스크에서 값을 바꿔치기하면 검증이 실패한다.
3. **fail-closed.** 기록과 서버 설정이 어긋나거나, TPM 해제·검증이 실패하면 봉인 상태를 유지하고 오류를 낸다.
   다른 방식으로 자동 전환하거나 초기화하지 않는다. 이전 도중 실패는 되돌린다 (기록 저장 실패 → blob 삭제, blob 삭제 실패 → 기록 복원).
4. **복구 조각 모델.** TPM 모드에서도 *같은 루트 키의* Shamir 조각(5/3)을 발급한다. TPM 해제가 실패하면(장치 고장, blob 손상) 조각 3개로 해제한다.
   해제 후에도 기록은 tpm으로 남는다. HashiCorp Vault의 auto-unseal + *recovery key* 와 같은 발상이다. 차이: Vault의 recovery key는
   루트 키를 풀지 못하고 관리 작업(재생성 등)의 승인에만 쓰이지만, 여기서는 복구 조각이 *루트 키 자체*를 복원한다 — 외부 KMS 없이 단일
   장치 고장을 견디려면 루트 키를 복원할 수단이 별도로 있어야 하기 때문이다. 그만큼 복구 조각 보관이 중요하다(탈취 시 TPM과 무관하게 루트 키 노출).
5. **TPM 모드의 자동 해제 허용.** `KMS_AUTO_UNSEAL` 거부 규칙은 Shamir 모드에만 적용한다. Shamir에서 자동 해제를 금지한 이유는 "사람의
   정족수가 통제의 본질"이기 때문이다. TPM 모드는 그 통제를 장치 소유로 바꾸는 것이 *목적*이므로, 기동 시 TPM 해제를 시도하는 것이 정의상 맞다.
6. **PCR 기본 끔.** PCR 봉인은 부팅 체인 변조를 막지만, 정상적인 커널·펌웨어 업데이트에도 PCR이 바뀌어 자동 해제가 실패한다.
   무인 복구가 이 기능의 존재 이유이므로 기본은 끄고(`KMS_TPM_PCRS` 미설정), 켜면 업데이트마다 복구 조각 또는 재이전이 필요함을 감수한다.
7. **swtpm의 한계.** 현재 노드에는 실물 TPM이 없어 swtpm(소프트웨어 TPM, 상태는 디스크 파일)을 `tpm_vtpm_proxy`로 노출한다.
   같은 디스크를 가진 공격자에게는 보호가 아니다. 이 배포가 보이는 것은 "실제 장치 경로로 동작하는 구조"이며, 실물/클라우드 vTPM으로 옮기면
   코드 수정 없이 `KMS_TPM_DEVICE`만 바꿔 하드웨어 보호를 얻는다. 서버는 CGO 없이 순수 Go로 장치를 연다(시뮬레이터는 `tpm_lab` 테스트에서만).
8. **조각 재발급은 유출 대응이 아니다.** `shamir → shamir`는 *같은 루트 키를 다시 나눈* 것이라 이전 조각도 계속 유효하다. 조각이 유출됐다면
   필요한 것은 루트 키 교체(rekey: 모든 KEK를 새 루트 키로 재포장)이고 **미구현**이다. 응답과 문서에 이 경고를 명시한다.

**대안과 기각**
- *이전 시 새 루트 키 생성 후 전체 재암호화*: 운영 Secret의 가용성 위험이 크고 rekey 자체가 별도 과제 — 기각.
- *TPM 실패 시 자동으로 Shamir 경로로 전환*: 조각이 없는 상태에서의 "자동 전환"은 없다. 봉인 상태로 뜨고 사람이 조각을 넣는다 — 명시적 복구만 허용.
- *TPM blob을 init 기록에 넣기*: 기록은 방식 선언, blob은 장치 종속 데이터라 수명이 달라 분리(`seal/tpm/rootkey`).

**대가**
- TPM 모드는 단일 장치(또는 swtpm 상태 파일)에 대한 신뢰가 추가된다. 복구 조각이 이를 보완하지만, 조각 보관 규율이 느슨해지면 Shamir 모드보다 약해질 수 있다.
- 한 서버 안에서 두 방식을 오가므로 `seal` 패키지에 `Switch`가 생겼고, 해제 경로가 "복구 조각 완성 → Shamir, 아니면 TPM"의 우선순위를 갖는다.

**배포 보류 결정과 근거 (운영 서버 시험 결과)**

코드(seal 패키지, `seal-migrate`, init 기록 v2, `recovery_available`, 복구 조각 모델)는 그대로 유지하고, 운영 배포 기본값은 Shamir 전용
(`KMS_SEAL_ALLOWED=shamir`, 이 경우 `seal-migrate target=tpm`은 403 `seal_not_allowed`)이다. 이유:

| 근거 | 내용 | 확인 방법 |
|---|---|---|
| 컨테이너가 장치를 못 연다 | 비특권 시험 Pod(uid 10001, supplementalGroups=tss gid)가 hostPath로 넣은 `/dev/tpmrm0`을 열면 `Operation not permitted`. 파일 권한은 정상이고 쿠버네티스 **장치 cgroup**이 막는다 | **서버 실행으로 확인** |
| hostPath 빈 디렉터리 | type 없는 hostPath가 없는 장치 경로를 마운트하면 호스트에 **빈 디렉터리**가 생긴다(`rmdir`로 복구). 장치 생성을 막을 수 있다 | **서버 실행으로 확인** |
| swtpm 자체는 동작 | swtpm 0.7.3 + `tpm_vtpm_proxy`로 `/dev/tpmrm0` 생성 성공. 단 Ubuntu **AppArmor** swtpm 프로필 때문에 로컬 규칙이 필요했고 `--runas tss`는 `/dev/vtpmx` 권한 오류라 제거(상태 폴더 root:root 0700) | **서버 실행으로 확인** |
| CDI 주석 무시 | containerd 2.2.1(`enable_cdi=true`)에서 CDI 설정 파일 + Pod 주석 `cdi.k8s.io/...`을 써 봤지만 주석이 조용히 무시되어 장치가 들어가지 않음 | **서버 실행으로 확인** |
| containerd 취약점 | 2.2.1은 CVE-2026-53492(체크포인트 복원 시 CDI 주석을 신뢰; 2.1.9 / 2.2.5 / 2.3.2에서 수정)에 해당. 시험용 CDI 설정 파일은 지움. 재개 전에 containerd를 2.2.5 이상으로 올려야 한다 | 서버에서 버전 확인 + 공개 권고(문서로 본 것) |
| 보호 이득이 작다 | swtpm은 상태를 **같은 디스크**의 파일로 둔다 → 디스크/root를 가진 공격자에게는 이득 없음. 자동 해제 때문에 재시작에 조각이 필요 없어져 오히려 Shamir의 "정족수 통제"보다 **약해지는 면**도 있다 | 설계 판단 |

**하드웨어 TPM으로 옮길 때의 설계 (구현하지 않음, 문서만)**: 전용 NRI 플러그인 `cmd/kms-tpm-nri`.
- 조건: 네임스페이스 `kube-system` + Pod 이름 접두 `kms-core-` + 컨테이너 이름 `kms` + 주석 `kubernetes.io/config.source=file`(static pod)일 때**만**
  `/dev/tpmrm0`을 컨테이너에 넣고, 장치 cgroup에서 **그 장치만** rw로 허용(gid `tss`, 0660).
- 장치가 없으면 넣지 않는다 → KMS는 봉인 상태로 떠서 조각으로 복구한다(빈 디렉터리 함정도 없음).
- 설치: `/opt/nri/plugins/10-kms-tpm`에 두고 containerd 재시작 1회. 사전 등록 플러그인이라 재부팅 시 KMS Pod보다 먼저 준비된다.
- 하드웨어 TPM으로 이전할 때는 swtpm 서비스만 빼면 된다(코드·플러그인 동일).
- **확인이 남은 항목(코드를 읽고 검증할 것)**: `kubernetes.io/config.source=file` 주석을 API로 Pod를 만들어 흉내 낼 수 없다는 점은 kubelet 코드로
  확인해야 한다 — 이 가정이 틀리면 아무 Pod나 장치를 얻는 우회가 생긴다.

**버린 대안**
| 대안 | 버린 이유 |
|---|---|
| Pod 주석 방식 CDI(`cdi.k8s.io/...`) | 2.2.1에서 주석이 무시되어 동작하지 않았고, 주석을 신뢰하는 경로 자체가 CVE-2026-53492의 원인 |
| containerd NRI 예제 `device-injector` | 아무 Pod의 주석이나 믿고 장치·호스트 마운트를 넣어 준다 → 클러스터 내 Pod 생성 권한자가 호스트 장치를 얻는 권한 상승 경로 |
| `privileged: true` | 컨테이너에 모든 장치·권한을 주는 과도한 권한 확대. KMS 하드닝(`readOnlyRootFilesystem`, capability drop)과 맞지 않음 |
| swtpm을 소켓 방식으로 연결 | 컨테이너 장치 접근 문제(= 하드웨어 TPM으로 옮길 때의 문제)와 무관한 우회라 하드웨어 이전에 쓰이지 않고, 같은 디스크 상태라는 swtpm의 한계도 그대로 |
| hostPath type `CharDevice` | 장치가 없는 노드/부팅 순서에서 Pod가 시작하지 못해 "봉인 상태로 떠서 조각 복구" 경로를 잃는다 |

**실행으로 확인한 것 vs 문서로만 본 것**: 위 표의 "서버 실행으로 확인" 항목은 운영 서버에서 직접 확인했다. 코드 동작(자동 해제, 복구 조각, 이전·되돌림,
실패 시 롤백)은 시뮬레이터(`tpm_lab`)와 가짜 TPM 단위 시험으로만 확인했고 **운영 클러스터에서 실행해 보지 않았다.** CVE 내용과 NRI 플러그인 설계는 문서로만 본 것이다.

## ADR-011. Transit 요청 감사는 비동기로 기록한다

**상태**: 구현 완료, 서버 적용 전

**배경**
관리 감사(`internal/audit`)는 요청마다 동기 쓰기 + fsync다. 관리 작업은 드물어 괜찮지만 Transit(encrypt/decrypt/rewrap)에
적용하면 요청 하나가 디스크 왕복만큼 느려져 처리량이 크게 떨어진다(벤치 동시16 2,104/s 수준이 fsync 속도에 묶임).
그러나 "누가 어떤 키를 썼는가"는 감사 요구의 핵심이다.

**결정**: 버퍼 채널 + 배치 쓰기 + 주기 fsync(기본 1초) 의 비동기 기록기. 요청은 이벤트를 큐에 넣고 바로 돌아간다.
- 기록: 시각, 요청 ID, 주체, 동작, **키 이름**, SAR 판단 네임스페이스, 결과 코드, 지연(필요 시 내부 사유). 본문·토큰·평문·암호문은 필드 자체가 없다.
- 버퍼가 가득 차면 **요청을 막지 않고 이벤트를 버리고** `kms_audit_dropped_total`을 올린다.
- 정상 종료 시 남은 기록을 flush한다.
- 관리 감사 파일 형식·위치는 바꾸지 않았다(선택 필드 `key`만 추가). Transit 감사는 별도 디렉터리(`KMS_TRANSIT_AUDIT_DIR`, 비우면 끔).

**트레이드오프(정직하게)**
- **완전성 vs 가용성**: 감사 완전성이 *보장되지 않는다*. 버퍼 포화 시 유실, 비정상 종료(kill -9, 정전) 시 마지막 fsync 이후 약 1초분 유실.
  유실은 지표로 드러나지만(포화) 비정상 종료분은 드러나지 않는다. "감사 기록이 없으면 요청을 거부"하는 fail-closed 모델은
  Transit 처리량과 가용성을 감사 디스크에 묶으므로 택하지 않았다. 관리 평면(키 생성/삭제 등 되돌릴 수 없는 작업)은 동기 감사를 유지한다.
- 인증 실패(401)는 주체를 알 수 없어 기록하지 않는다(`kms_transit_requests_total`로 센다).
- 하루 파일 상한 256 MiB, 30일 보존. 상한 초과분도 버리고 지표를 올린다.

## ADR-012. 키 삭제는 사용 중지 → 삭제 예약 → 삭제 3단계

**상태**: 구현 완료, 서버 적용 전

**배경**: 키 삭제는 되돌릴 수 없고, 그 키로 암호화한 데이터를 영구히 못 읽게 만든다. 실수 한 번이 데이터 소실이다.

**결정(AWS KMS의 모델과 같은 형태)**
- 상태: `active` / `disabled` / `pending_deletion(deletion_date)`. 필드가 없는 기존 키는 active.
- `disable`로 먼저 사용을 멈추고 오류가 나는지 지켜본다(암복호화는 409 `key_not_active`, 자동 회전 건너뜀) → `schedule-deletion`
  (유예 7~30일, 기본 30) → 유예 후 백그라운드 작업이 키 자료를 삭제. `cancel-deletion`은 `disabled`로 돌아간다(AWS와 같이 바로 쓰이지 않고 `enable`이 필요).
- 삭제는 봉인 해제 상태에서만, 삭제 직전·직후 관리 감사에 기록하며 감사 기록이 실패하면 지우지 않고, storage의 원자적 Delete 한 번으로 한다.
- **보호 키**: KMS v2 경로의 키(`kmsv2.New`가 자동 등록)와 `KMS_PROTECTED_KEYS`의 키는 disable·schedule-deletion을 거부(409 `key_protected`)하고,
  상태와 무관하게 항상 사용 가능하다. KMS v2 키를 잃으면 etcd의 모든 Secret이 읽히지 않으므로 설정이 비어 있어도 코드가 지킨다.

**AWS와 비교**: 같은 점 — 유예 7~30일, 기본 30, 취소 시 disabled 복귀, 비활성 키 사용 거부. 다른 점 — 삭제 전에 `min_decryption_version`을 올려 "옛 버전만" 차단하는 단계가
따로 가능하고, 코드가 지키는 보호 키(KMS v2 키)가 있다.
삭제 후 같은 이름의 키를 새로 만들 수 있지만 옛 암호문은 영구히 복호화되지 않는다.

**대가**: 유예 동안 키 자료가 남아 있다(의도). 삭제 시각의 정밀도는 점검 주기(기본 10분)에 묶인다.

## ADR-013. data key API (봉투 암호화를 클라이언트에 위임)

**상태**: 구현 완료, 서버 적용 전

**배경**: Transit `encrypt`는 평문 전체를 KMS로 보낸다. 큰 데이터(본문 상한 2 MiB 초과)나 성능이 중요한 경로에서는 부적합하다.

**결정**: `POST /v1/datakey/{name}` — KMS가 1회용 데이터 키(128/256비트)를 `crypto/rand`로 만들고, **기존 encrypt와 같은 경로**
(같은 키 링 최신 버전, 같은 AAD, 같은 `kms:v{n}:` 형식)로 봉인해 `{ciphertext, plaintext, key_version}`을 돌려준다(`plaintext=false`면 암호문만).
클라이언트는 평문 키로 자기 데이터를 로컬에서 암호화하고 평문 키를 버린 뒤 **암호문 키만 저장**한다. 나중에 기존 `decrypt`로 평문 키를 되찾는다
(AWS GenerateDataKey와 같은 모델).

**근거**
- 새 암호 형식을 만들지 않고 encrypt 경로를 재사용해, 키 회전·`min_decryption_version`·비활성 키 거부·감사가 그대로 적용된다.
  회전 후에도 이전 data key 암호문은 정책이 허용하는 한 복호화된다.
- 새 verb `datakey`로 SAR 인가한다 — "데이터 키를 만들 수 있는 주체"와 "임의 평문을 암호화할 수 있는 주체"를 분리할 수 있다. C+B 규칙은 그대로.
- 평문 키는 응답 본문에만 있고 서버는 응답 후 0으로 지운다. 로그·감사(본문 필드 없음)·지표(길이만)에 남기지 않는다.

**대가**: 평문 키가 네트워크로 나간다(TLS 필수). 데이터 암호화의 정확성(nonce 재사용 금지 등)은 클라이언트 책임이다.

## ADR-014. 외부 사용자 경로 ③ — 인터넷 공개 리스너와 방어선 3개

**상태**: 구현 완료, 서버 적용 전 (리스너는 켜지지만 방화벽을 사람이 열기 전에는 외부에 닿지 않는다)

**배경**: 외부 사용자가 KMS를 쓰게 하는 경로로 ① 클러스터 안 Pod, ② tailnet 전용 노출, ③ 인터넷 공개를 비교했다.
tailnet 전용은 **사용자마다 초대·클라이언트 설치·ACL 항목이 필요**해 외부 사용자 수가 늘면 운영 부담이 사용자 수에 비례한다.
인터넷 공개는 사용자에게 주소·CA 인증서·토큰만 주면 된다. 대신 공개 포트의 위험을 코드로 막아야 한다.

**결정**: 별도 리스너 `KMS_EXTERNAL_ADDR`(기본 꺼짐, 템플릿 `0.0.0.0:9443`)를 둔다. 같은 TLS 인증서(ADR-015)를 쓰고, 라우트는
`POST /v1/encrypt|decrypt|rewrap|datakey/{name}`와 `GET /healthz`뿐이다(sys, seal-profile, 관리 기능 없음 → 공개 면적 최소). 방어선 3개:

1. **요청자 네임스페이스 제한** (`KMS_EXTERNAL_SUBJECT_NAMESPACES`, 기본 `kms-external`): 내부 SA 토큰이 유출돼도 인터넷에서는 쓸 수 없다.
   (내부 토큰은 같은 audience라 서명 검증만으로는 통과하므로 별도 제한이 필요하다.)
2. **키 네임스페이스 제한** (`KMS_EXTERNAL_KEY_NAMESPACES`, 기본 `kms-external`): 키는 `kms-external.<이름>`만. 전역 키·다른 팀 키·없는 키·형식 오류는
   모두 같은 403이라 키 존재 여부를 알아낼 수 없다. SAR 이전에 걸러 apiserver 부하도 줄인다. 이후 ADR-009의 SAR이 다시 판단한다(방어선이 겹친다).
3. **요청 수 제한 + 인증 실패 차단**: 클라이언트 IP별 토큰 버킷(기본 20/s, burst 40) → 429 `rate_limited`, 401이 IP당 1분에 10회를 넘으면 5분 차단.
   IP는 TCP `RemoteAddr`다 — `X-Forwarded-For`는 클라이언트가 위조할 수 있어 신뢰하지 않는다(프록시 없이 직접 받는다). 추적 맵은 1만 개 상한 + 정리가 있어
   메모리가 늘지 않는다.

관측: `kms_external_requests_total`, `kms_external_rejected_total{reason=rate|authfail}`, `kms_external_blocked_ips`(개수만). 감사에는 `listener:external`과 클라이언트 IP.

**대가/한계**
- IPv6는 주소 단위로 센다(/64 단위 묶음 없음) → 한 사용자가 주소를 바꿔 가며 한도를 우회할 수 있다. 공격 규모가 커지면 앞단(방화벽/WAF)이 필요하다.
- 토큰은 개별 회수가 안 된다 → 수명을 짧게(기본 1시간, 최대 24시간)로 완화하고, SA 삭제로 이후 검증을 막는다.
- 단일 노드 단일 인스턴스라 DoS에 대한 가용성은 보장하지 않는다. 요청 수 제한은 보호막일 뿐이다.
- 외부 사용자는 내부 CA를 신뢰해야 한다(공인 인증서 미사용). CA 공개 인증서 배포 절차는 docs/usage.md.

## ADR-015. TLS 인증서 무중단 교체

**상태**: 구현 완료, 서버 적용 전

**배경**: 인증서는 시작 시 한 번만 읽어서, 교체(만료 갱신, SAN 추가)하려면 KMS를 재시작해야 했다. KMS 재시작은 **봉인 → 조각 3개**를 뜻한다.

**결정**: `tls.Config.GetCertificate`에서 캐시된 인증서를 주되, 마지막 확인 후 30초가 지났을 때만 파일 mtime·크기를 보고 바뀐 경우에만 다시 읽는다.
새 파일을 읽다 실패하면(반쯤 쓴 파일, 인증서·키 불일치) **이전 인증서를 계속 쓰고 로그를 남긴다**. Transit과 외부 리스너가 같은 재로더를 쓴다.
권장 교체 방식은 임시 이름으로 쓴 뒤 `mv`(원자적, `scripts/reissue-transit-cert.sh`가 그렇게 한다).

**근거**: 핸드셰이크마다 디스크를 읽지 않으려는 캐시, 갱신 실수가 장애로 번지지 않게 하는 fail-safe(이전 인증서 유지). 
**한계**: 교체 후 반영까지 최대 30초. 이미 맺어진 연결은 옛 인증서로 계속된다. 키 파일을 먼저 바꾸고 인증서를 나중에 바꾸는 사이에는 불일치로 보고 이전 인증서를 유지한다(다음 확인에서 해소).

## ADR-016. 연결 재사용 버그 수정 (TLSClient의 Transport)

**상태**: 수정 완료 (커밋 2080d1e), 측정으로 확인

**증상**: 동시성을 올릴수록 처리량이 *떨어졌다* — transit 동시성 1: 832 req/s, 4: 378, 16: 224, 32: 182 (`bench-results/cloud-1014-1604`).

**원인**: `security.TLSClient`가 `&http.Transport{TLSClientConfig: ...}`만 만들어 Go의 기본값 `MaxIdleConnsPerHost=2`가 적용됐다. 동시 요청이 3개 이상이면
초과 연결은 응답 뒤에 닫히고, 다음 요청이 TLS 핸드셰이크부터 다시 한다(동시성 16: 새 TCP 연결 2,064개). *요청마다 새 Transport를 만든 것이 아니라*,
하나의 Transport가 유휴 연결을 2개까지만 보관한 것이다. 측정 도구와 포털·관리 API가 모두 이 클라이언트를 써서 증상이 서버 한계처럼 보였다.

**수정**: `http.DefaultTransport.Clone()`에 TLS 설정(1.2+, CA)을 넣고 `MaxIdleConns=256`, `MaxIdleConnsPerHost=64`, `IdleConnTimeout=90s`를 명시. Proxy는 nil(기존 동작 유지),
타임아웃·리다이렉트 거부는 그대로. 테스트: 16 고루틴 × 50요청 뒤 새 연결 수 ≤ 32 (수정 전 241로 실패).

**측정**(`bench-results/cloud-fix-1015/summary.csv`, 같은 환경 재측정): 동시성 16에서 **224 → 2,104 req/s**(약 9.4배), 동시성 4: 378 → 1,908, 32: 182 → 1,871. 동시성 1은 832 → 819로 변화 없음(원래 연결 1개).

**교훈**: 클라이언트 쪽 기본값이 서버 성능 측정을 왜곡할 수 있다. 동시성이 올라갈 때 처리량이 내려가는 곡선은 서버 한계가 아니라 연결 수립 비용을 먼저 의심한다. 새 HTTP 클라이언트(CLI의 `cmd/kms` 포함)도 같은 Transport 설정을 쓴다.

## ADR-017. 관리 화면 v2 — 기존 화면 보존, 관리/사용자 분리

**상태**: 구현 완료

**결정**
- 새 관리 화면은 `/v2/`(`internal/adminapi/ui2`, 의존성 없는 정적 파일)에 두고 **기존 화면(`/console`, `/dashboard`)은 그대로 둔다**(백업 겸 되돌리기 수단; `ADMIN_API_UI_DEFAULT=v1`이면 `/`가 기존 화면으로 간다).
  두 화면은 같은 API 허용 목록을 쓴다.
- **관리자 화면과 사용자 화면을 분리**한다: 관리 화면은 tailnet 안의 운영자(역할 파일의 admin/viewer)용이고, 앱 개발자·외부 사용자용 화면은 사용자 포털(ADR-018)과 CLI(ADR-019)다.
  관리 화면에는 키 사용(암복호화) 기능을 넣지 않는다.
- 역할: viewer에게는 쓰기 컨트롤을 회색으로 잠그고, **키 수명 주기 같은 위험 동작 패널은 아예 그리지 않는다.** 위험 동작(사용 중지·삭제 예약)은 키 이름을 다시 입력해야 실행된다.
  화면의 역할 처리는 편의일 뿐이고 서버(`Security.Wrap`: 역할·CSRF)가 최종 판단한다.
- **관리 API 허용 목록**(`internal/adminapi/router.go`)에 있는 경로만 소켓으로 중계한다. `uipaths_test.go`가 화면이 부르는 경로와 허용 목록을 대조해 어긋나면 실패시킨다.
  `/v1/sys/seal-migrate`는 허용 목록에 없다: 조각 재발급(`target=shamir`)도 init 기록을 v2로 올려 이전 서버 이미지로 되돌릴 수 없게 되므로, 이번 운영 적용 동안은 서버의 관리 소켓에서만 실행한다.
- 봉인 화면은 TPM 전환 버튼 없이 "배포 보류(ADR-010)" 안내만 보여 준다. 감사 화면은 관리 감사와 Transit 감사를 합쳐 키·경로(관리/내부/외부)로 거를 수 있다.

**대가**: 화면 파일이 두 벌이다(v1/v2). v1은 기능이 늘지 않으므로 충분히 안정화되면 제거를 검토한다.

## ADR-018. 사용자 포털 — tailnet 전용 시험 도구와 브라우저 안 파일 암호화

**상태**: 구현 완료

**결정**
- 포털(`cmd/demo-app`, `internal/demo`)은 **Tailscale 8443을 통한 tailnet 전용** 시험·시연 도구다(`scripts/deploy-user-portal.sh`). 인터넷에 공개하지 않는다. 사용자 토큰을 입력받는 모드(외부 사용자용)는 만들지 않았다 —
  외부 사용자는 CLI(ADR-019) 또는 외부 리스너(ADR-014)를 직접 쓴다.
- 포털 서버는 자기 서비스 계정(`kms-demo/app-a`) 토큰으로 KMS를 부르고, 브라우저는 토큰을 보지 못한다. 쓸 수 있는 키는 `DEMO_KEYS` 허용 목록으로 제한되며, "이 계정이 이 키를 써도 되는가"는 KMS(SAR)가 403으로 판단한다.
  화면 상단의 "…권한으로 동작해요" 상시 문구는 지우고, 403 안내 안에만 "(현재 app-a 권한)"으로 보여 준다.
- **파일 암호화 탭**: 브라우저가 포털 서버를 통해 data key를 받고(`POST /datakey` 중계), WebCrypto(AES-GCM)로 **브라우저 안에서** 암호화·복호화한다. **원문 파일은 서버로 가지 않는다**(업로드 경로가 없고 테스트로 확인).
  결과는 KMSF 형식(`pkg/kmsfile`)이라 CLI로도 풀 수 있고, Go↔브라우저 양방향 호환은 Node 상호운용 테스트로 확인했다. 1 GiB 이하 파일만 지원(브라우저 메모리).

**대가/한계**: 평문 data key가 포털 서버를 지나간다(서버는 저장·로그하지 않지만 포털 서버는 신뢰 경계 안이다). 큰 파일은 CLI가 적합하다.

## ADR-019. CLI와 KMSF 파일 형식

**상태**: 구현 완료

**결정**: 외부 사용자용 명령줄 도구 `kms`(`cmd/kms`: login / encrypt / decrypt / datakey / version)와, 큰 파일을 위한 봉투 암호화 형식 KMSF(`pkg/kmsfile`, 외부에서 import 가능한 `pkg/` 아래).
- **자동 선택**: 입력 1 MiB 이하는 Transit `encrypt`(결과는 `kms:v..` 문자열), 넘으면 `datakey` + KMSF 파일. 서버 본문 상한(2 MiB)과 base64 확장을 고려한 경계다. 복호화는 앞 4바이트(`KMSF`)로 형식을 판별한다.
- **형식**: 헤더(매직, 버전, 키 이름, data key 암호문, 청크 크기, 기본 nonce) + 64 KiB 청크별 AES-256-GCM. nonce = 기본 nonce XOR 청크 번호, AAD = SHA-256(헤더) | 청크 번호 | 마지막 청크 여부 →
  청크 교환·삭제·잘라내기·덧붙이기·헤더 변조를 모두 인증 실패로 탐지(STREAM 구성과 같은 발상). 스트리밍이라 파일 전체를 메모리에 올리지 않는다.
- **토큰 취급**: 기본으로 디스크에 저장하지 않는다(`KMS_TOKEN` 환경변수 또는 `--token-file`; 저장은 `--save-token`을 명시했을 때만, 0600). 토큰·평문은 오류 메시지에 넣지 않는다.
  복호화 실패 시 출력 파일을 남기지 않는다(임시 파일 후 rename).
- 배포: `scripts/build-cli.sh`(4개 플랫폼 + SHA256SUMS), `install.sh`(체크섬 검증 실패 시 설치 안 함, `~/.local/bin`).

**한계**: 서명 없이 SHA256SUMS만으로 무결성을 확인한다 — 배포 채널이 SUMS와 바이너리를 함께 바꿀 수 있으면 막지 못한다(서명은 이후 과제). KMSF는 형식 버전 1이며 data key 회전(재포장) 도구는 아직 없다.

## ADR-020. 외부 리스너는 인증·인가가 완전하지 않으면 뜨지 않는다 (fail-closed)

**상태**: 구현 완료

**배경(발견한 결함)**: 외부 리스너(ADR-014)는 Transit 라우터와 같은 미들웨어를 쓰는데, 인증기(Verifier)나 인가기(Authorizer)가 `nil`이면 해당 검사를 *건너뛰는* 것이 기존 동작이다(격리된 테스트용).
그래서 `KMS_AUTHN`/`KMS_AUTHZ`가 꺼진 설정에서 `KMS_EXTERNAL_ADDR`만 주면, 인터넷에 열린 포트가 토큰 검사나 SAR 없이 동작해 kms-external 키를 누구나 쓸 수 있게 된다.
(현재 `main`은 운영에서 authn/authz 끄기와 fail-open을 기동 시점에 거부하므로 도달하기 어렵지만, 다른 경로로 리스너가 만들어지거나 그 검사가 바뀌면 열릴 수 있는 구멍이다.)

**결정(이중 방어)**
1. `cmd/server`: `KMS_EXTERNAL_ADDR`가 설정됐는데 Verifier/Authorizer가 없거나 `KMS_AUTHZ_FAIL_OPEN=true`이면 **외부 리스너를 띄우지 않고 이유를 로그로 남긴다.** 서버 전체와 내부 리스너는 정상 기동한다 — 외부 경로 하나 때문에 클러스터 Secret 경로(KMS v2)가 멈추지 않게 하려는 것이다.
2. `NewExternalRouter`: nil이 들어오면 모든 요청(`/healthz` 포함)을 503으로 거부한다.

**근거**: 공개 포트의 기본 상태는 "닫힘"이어야 한다. 내부 리스너는 기존 동작(nil이면 검사 생략)을 유지해 테스트 호환성을 지키고, 외부 리스너에만 더 엄격한 규칙을 둔다.
