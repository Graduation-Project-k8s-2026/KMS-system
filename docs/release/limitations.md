# 범위와 남은 제약

최신 실행 상태는 [verification.md](verification.md), 실제 이미지·버전은 [release-lock.json](release-lock.json)이다. §12의 실제 apiserver 연결·전체 현재 Secret 암호화·identity 제거·KEK 회전은 완료했다. 과거 문서의 “KMS 연결 미실행”은 최초 §5.2 작업 당시의 이력이다.

- 사용자 지시로 §10의 데모 앱·추가 시나리오는 보류했고 §18은 작업 지시로 사용하지 않았다. 앱이 실제 배포·시연된 것으로 표시하지 않는다.
- 단일 노드와 하나의 Boot Volume이다. local PV/PVC는 HA·디스크 장애 격리가 아니다. Flannel 배치만으로 NetworkPolicy 강제를 주장하지 않는다.
- 호스트 root·커널·메모리 접근 권한은 신뢰 경계 안이다. Root/KEK는 unsealed 프로세스 RAM에 있으며 Go의 완전한 메모리 소거를 보장하지 않는다.
- **부팅 공백**: 운영은 Shamir 모드라 **유지된다**(재부팅마다 조각 3개). TPM 모드에서는 해소되지만 TPM 배포는 보류다(아래). Shamir 모드는 기존 share를 가진 사람의 개입이 필요하고, 한 사람이 모든 share를 보관하면 다인 통제가 아니다. 무인 재부팅 복구를 주장하지 않는다.
- **루트 키 교체(rekey) 미구현**: 봉인 방식 이전·조각 재발급은 *같은 루트 키*를 다시 봉인/분할할 뿐이다. 조각이 유출돼도 이전 조각은 계속 유효하며, 유출 대응(루트 키 교체와 전체 KEK 재포장)은 아직 없다.
- **TPM 봉인: 코드 구현·시뮬레이터 검증, 배포 보류(장치 cgroup), 운영은 Shamir** (ADR-010). 비특권 컨테이너는 hostPath로 넣은 `/dev/tpmrm0`을 장치 cgroup 때문에 열 수 없고(서버에서 확인), 해결(하드웨어 TPM + 전용 NRI 플러그인)은 설계만 있고 구현하지 않았다. `seal-migrate target=tpm`은 `KMS_SEAL_ALLOWED=shamir`에서 403으로 거부된다. 운영 클러스터에서 TPM 자동 해제를 실행해 본 적이 없다.
- **swtpm은 하드웨어 보호가 아니다**: swtpm 상태는 디스크의 파일이라 같은 디스크를 가진 공격자에게는 TPM 봉인이 보호가 되지 않는다. 재개하더라도 이 배포는 실제 TPM 장치 경로로 동작하는 구조의 검증이며, 하드웨어 보호는 실물/클라우드 vTPM으로 옮겨야 얻는다. PCR은 기본 꺼짐(켜면 커널/펌웨어 업데이트 후 자동 해제가 실패할 수 있음).
- **containerd는 2.2.5 이상(또는 2.1.9 / 2.3.2)으로 올려야 한다(CVE-2026-53492)**: 현재 2.2.1은 체크포인트 복원 시 CDI 주석을 신뢰하는 취약점에 해당한다. TPM 배포 재개 여부와 무관하게 업그레이드가 필요하다(시험용 CDI 설정 파일은 이미 삭제했다).
- Plugin Job은 강한 KMS UDS 권한을 가진 시험이다. Transit/E2E와 같은 권한으로 간주하지 않는다. 모든 사람에게 hostPath/hostNetwork Pod 생성 권한을 제공하지 않는다.
- 실제 tailnet 외부/비승인 기기 접속·IPv6 차단·MFA·기기 회수는 사람이 접근 가능한 해당 기기에서 추가 검증해야 한다. 호스트 loopback admin 시험은 사람 로그인 시험이 아니다.
- TLS/SA 공개키/SAR 인증서는 시작 시 로드한다. 교체에는 계획된 재시작·기존 share 입력이 필요하다. 개별 Transit JWT 즉시 회수·CRL/OCSP·hot reload를 주장하지 않는다. SAR 캐시/토큰 수명에 따른 지연이 있다.
- 현재 etcd Secret 전체가 KMS v2여도 과거 revision·기존 snapshot에 평문이 남을 수 있다. compaction/defrag/보존 정책과 외부 백업 삭제는 별도다. 이전 KEK를 삭제하지 않는다.
- 이번 성능 측정은 3회·100왕복·동시성1·1024 bytes의 단일 노드 실험이다. 서비스 공유·운영 조회 간섭이 있으며 일반 환경의 성능 우열로 확장하지 않는다.
- K8sSeal 측정은 fake client, TPM은 CGO simulator다. 별도 실제 클러스터·실물 TPM의 보안성/지연을 측정한 것이 아니다. 같은 클러스터 Secret을 Root 저장소로 쓰는 순환 의존은 사용하지 않는다.
- 외부 백업은 암호화 파일을 별도 장치로 옮기고 목적지 hash를 확인해야 완료다. 같은 인스턴스의 `/var/backups` 파일은 외부 백업이 아니다. 이번 최종 묶음은 운영자의 PC 반출·별도 복구 암호 보관·목적지 SHA256 일치 확인을 받았다. 백업 이후의 재부팅 감사 기록과 추가 Transit smoke 결과는 해당 snapshot의 RPO 범위 밖이다.
- 현재 소스는 미커밋 작업 트리다. 기존 사용자 `cmd/bench/release.go` 변경을 유지했으며 배포된 bench image의 source provenance와 현재 호스트 도구 소스를 혼동하지 않는다.
- **인가 모델이 바뀌었다(C+B, ADR-009)**: 점 없는 기존 키는 전역 키라 ClusterRole/ClusterRoleBinding으로만 허용된다. 이전 도구가 찾지 못한 권한(예: resourceNames 없는 Role로 받던 전역 키 접근)은 적용 후 403이 된다. 소유 팀 키(`<ns>.<name>`)의 소유는 키 이름만으로 정해지므로, 어떤 이름으로 키를 *만들*지는 관리 소켓 접근 권한(관리자)으로만 통제한다.
- **Transit 감사는 완전성을 보장하지 않는다(ADR-011)**: 버퍼 포화 시 유실(`kms_audit_dropped_total`), 비정상 종료 시 마지막 fsync 이후 약 1초분 유실. 인증 실패(401)는 기록하지 않는다.
- **키 삭제는 되돌릴 수 없다(ADR-012)**: 유예가 끝나 삭제된 키의 암호문은 영구히 복호화되지 않는다. 삭제 시각은 점검 주기(기본 10분) 정밀도다. 외부 백업에 남은 옛 키 자료는 별도로 폐기해야 한다.
- **TLS 인증서 교체는 무중단이 되었다(ADR-015)**: 파일을 바꾸면 최대 30초 안에 반영되고 재시작/조각 입력이 필요 없다. 단 이미 맺어진 연결은 옛 인증서로 계속되고, CA 자체를 바꾸면 클라이언트 신뢰 설정은 별도다. (이전 한계 "인증서 교체에는 계획된 재시작이 필요"는 Transit 인증서에 대해 해소됨. SA 공개키·SAR 인증서는 여전히 시작 시 로드.)
- **외부(인터넷) 경로의 남은 한계(ADR-014)**: 토큰은 개별 회수가 안 된다(짧은 수명으로 완화: 기본 1시간, 최대 24시간; SA 삭제 후에는 새 검증이 막히지만 이미 유효한 서명은 만료까지 통과할 수 있다). 클라이언트 IP별 제한이라 IPv6 주소 회전/대규모 분산 공격에는 약하다. 단일 노드라 DoS 시 가용성은 보장하지 않는다. 외부 사용자는 내부 CA를 신뢰해야 한다.
- **data key는 평문 키를 네트워크로 보낸다(ADR-013)**: TLS가 전제이고, 데이터 암호화(nonce 관리 등)의 정확성은 클라이언트 책임이다.
